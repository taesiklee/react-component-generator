# TDD Rule

> **경고: 이 규칙은 Rigid(엄격) 규칙이다. 상황에 맞게 변형하지 마라.**
> 예외를 두고 싶다면 규칙을 어기지 말고, 아래 "프로젝트별 규칙 우선 조항"에 따라 프로젝트 문서에 명시적으로 예외를 기록하라.

## 1. 적용 기준

### TDD를 반드시 적용해야 하는 대상

- **비즈니스 로직** (도메인 규칙, 계산, 상태 전이)
- **API** (요청/응답 처리, 라우팅 핸들러 내부 로직)
- **유틸리티 함수** (순수 함수, 데이터 변환)
- **버그 수정** (재현 테스트 없는 수정은 수정이 아니다)

### TDD가 불필요한 대상

- **타입 정의** (interface, type alias)
- **설정 파일** (config, env, build script)
- **순수 UI** (마크업/스타일만 있고 로직이 없는 컴포넌트)
- **SQL** (스키마, 마이그레이션 — 단, 마이그레이션이 데이터 변환 로직을 포함하면 적용 대상)

판단이 애매하면 **적용하는 쪽**을 기본값으로 한다.

## 2. RED-GREEN-REFACTOR 사이클

### RED

- **하나의 동작 = 하나의 테스트.** 여러 동작을 한 테스트에 욱여넣지 않는다.
- 테스트를 작성한 즉시 **반드시 실행해서 실패를 눈으로 확인**한다. 실행하지 않고 다음 단계로 넘어가지 않는다.
- 실패 이유는 반드시 **"기능 미구현"**이어야 한다. 문법 오류, import 누락, 오타로 인한 실패는 RED가 아니다 — 고치고 다시 확인한다.

### GREEN

- 테스트를 통과시키는 **최소한의 코드만** 작성한다. YAGNI: 지금 테스트가 요구하지 않는 기능은 만들지 않는다.
- **신규 테스트와 기존 테스트 모두 통과**하는지 확인한다. 신규 테스트만 보고 넘어가지 않는다.

### REFACTOR

- 중복 제거, 이름 개선, 헬퍼 추출 등 **구조 개선만** 수행한다.
- 전체 테스트가 **green으로 유지**되는지 매 변경마다 확인한다.
- 이 단계에서 **새로운 동작을 추가하지 않는다.** 새 동작이 필요하면 다음 사이클의 RED로 넘긴다.

### 반복

- REFACTOR가 끝나면 다음 동작에 대한 **RED로 돌아간다.** 사이클을 건너뛰지 않는다.

## 3. 삭제 강제 규칙

- 테스트보다 프로덕션 코드를 먼저 작성했다면, **그 코드를 삭제하고 RED부터 다시 시작**한다.
- "나중에 테스트할 참고용"이라며 남겨두는 것도 **금지**한다. 예외 없다.

## 4. 변명 차단표

| 변명 | 반론 |
|---|---|
| 너무 단순해서 테스트 불필요 | 단순한 코드일수록 테스트 작성 비용도 낮다. "단순함"은 생략 근거가 아니라 작성이 쉬운 이유다. |
| 나중에 추가하겠다 | "나중"은 오지 않는다. 지금 없는 테스트는 영원히 없는 테스트다. |
| 시간이 없다 | 테스트 없이 짠 코드의 디버깅 시간이 테스트 작성 시간보다 길다. TDD는 시간을 아끼는 방법이지 쓰는 방법이 아니다. |
| 삭제하면 낭비다 | 검증 안 된 코드는 자산이 아니라 부채다. 남겨두면 "테스트 없이 통과된 코드"라는 나쁜 선례만 남는다. |
| 프로토타입이다 | 프로토타입은 반드시 버려지거나, 반드시 프로덕션이 된다. 버려질 게 확실하면 이 저장소 밖에서 작성하고, 아니라면 지금부터 TDD를 적용한다. |

## 5. 프로젝트별 규칙 우선 조항

- 이 문서는 **기본값(fallback)**이다.
- 프로젝트 루트의 `CLAUDE.md` 또는 `AGENTS.md`에 TDD 관련 규칙이 명시되어 있으면, **그 규칙을 이 문서보다 우선 적용**한다.
- 프로젝트 문서에 명시가 없는 항목만 이 문서의 규칙을 따른다.
